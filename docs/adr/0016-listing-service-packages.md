# Represent tiered offers as ServicePackages within Listings

**Status**: accepted

A `SERVICE` Listing may offer multiple selectable `ServicePackage`s, and a Buyer purchases exactly one package per `OrderItem`; `COURSE` Listings retain their existing single-price contract. Existing single-price SERVICE Listings are migrated to one initial package built from their current commercial contract, preserving existing order snapshots. P0 imposes no fixed maximum number of packages. Packages are options within the Listing rather than separately routable public identities; the Listing retains the public slug and presentation. Each package owns its name, scope, price, Processing Expectation, WarrantyPolicy, and ServiceInputFields; the selected package price is the amount held in escrow and the basis for the current Sub-Category commission. Public SERVICE Listing summaries use the lowest available package price, while the detail presents the package choices in ascending price order. Package changes follow the Listing's existing global post-moderation policy, with Admin moderation remaining at the Listing level and no separate approval gate. When multiple packages are available, the Buyer must explicitly choose one before adding it to the Cart; a single-package Listing may select it implicitly. A Seller may add a new package or edit a public package for future Buyers, but existing `OrderItem`s retain the accepted package snapshot. A Seller may make one package unavailable for new purchases while another package keeps the Listing purchasable; the last available package cannot be disabled while the Listing remains published, so stopping all sales requires pausing the Listing. A Cart entry pointing to an unavailable package remains visible but blocks Checkout until the Buyer changes the package or removes the entry. Reviews remain attached to `OrderItem`s and are shown in the shared Listing context with the purchased package identified, rather than creating a separate rating system per package. Packages that have been public or ordered are retained rather than hard-deleted so historical order snapshots and audit references remain valid. A Cart entry retains the selected package, while Checkout revalidates its current contract before money moves. We chose this over one Listing per price tier so related SERVICE offers share one public identity and storefront presentation, while the selected package remains part of the immutable order snapshot for fulfillment, disputes, reviews, and financial settlement.
